# ADR-004: ESP32-C3 — полноценная цель на ESP-IDF/FreeRTOS

- Статус: Accepted
- Дата: 2026-10-22
- Контекст: Phase 0

## Решение

ESP32-C3 — полноценная целевая плата MCFrame **с WiFi и BLE**. Поскольку
WiFi/BLE в ESP-IDF требуют FreeRTOS, на C3:

- планировщик — FreeRTOS;
- MCFrame предоставляет публичный API, HAL, лог, shell, crypto, OTA-протокол;
- MCFrame-планировщик и wait queues на C3 **не используются**;
- WiFi/BLE реализуются как `net::INetwork`/`net::IBle` поверх ESP-IDF.

## Почему не bare-metal

- `esp_wifi`/BLE-стек завязаны на FreeRTOS, event loop и свои задачи;
- second scheduler на одном ядре → гонки, starvation, непредсказуемые задержки;
- C3 — single-core RISC-V, отдельного ядра для радио нет.

## Приоритеты

- верхние приоритеты FreeRTOS зарезервированы под IDF (WiFi/BLE/таймеры);
- MCFrame-задачи отображаются в нижний диапазон (например, 5..12);
- `set_priority` не должен выводить задачу за разрешённый диапазон;
- точные значения фиксируются в Phase 4 по `sdkconfig`.

## WiFi/BLE

- `INetwork`: STA/AP/scan/connect/disconnect/events/caps;
- `IBle`: advertise/GATT server/notify/events;
- реализации: `esp_wifi`+`esp_netif`+`esp_event`, NimBLE;
- события IDF доставляются в задачу MCFrame, а не вызывают приложение из
  WiFi/BLE-контекста;
- credentials — в `nvs_flash`.

## OTA/boot/NVS

- boot — ESP-IDF bootloader + partition table; `os/boot` не используется;
- OTA — `esp_ota_*` + `esp_partition`;
- NVS — `nvs_flash` (обязателен для WiFi/BLE);
- `os/ota` MOLP может работать поверх UART/TCP как транспорт.

## Последствия

- На C3 «MCFrame-планировщик» не используется. Это осознанная цена WiFi/BLE.
- Нужен `backend_freertos` (ADR-001) и ESP-IDF component.
- Phase 4 — C3 без радио; Phase 5 — WiFi/BLE.
